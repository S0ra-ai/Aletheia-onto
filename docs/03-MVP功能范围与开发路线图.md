# MVP 功能范围与开发路线图

## 1. MVP 目标

MVP 的目标是证明“传统业务系统可以通过本体改造获得业务语义内核”，而不是一次性建成覆盖所有行业的完整平台。

首版必须完成一个可演示、可验证、可继续扩展的改造闭环：

```mermaid
flowchart LR
    A["连接传统数据库"] --> B["解析元数据"]
    B --> C["生成本体草案"]
    C --> D["人工确认本体"]
    D --> E["建立语义映射"]
    E --> F["配置业务规则"]
    F --> G["执行语义推理"]
    G --> H["输出语义服务"]
    H --> I["增强原业务场景"]
```

## 2. MVP 场景建议

建议首个 MVP 选择“合同管理”。

原因：

1. 业务对象清晰：客户、合同、付款计划、发票、履约事项。
2. 关系清晰：客户签订合同，合同产生付款计划，付款计划关联发票或收款。
3. 状态清晰：草稿、审批中、已生效、履约中、已完成、已终止。
4. 规则清晰：金额、日期、审批、付款、逾期、履约风险。
5. 展示效果直观：能清楚说明平台如何理解业务并给出风险提示。

若已有真实行业数据，也可以改选设备运维、项目管理或供应链采购。

## 3. MVP 范围

### 3.1 必须包含

1. 数据源管理：创建、测试、保存数据库连接。
2. 元数据采集：读取库、表、字段、索引、注释和样例值。
3. 数据画像：识别枚举字段、空值率、唯一值比例、字段样例。
4. 本体草案生成：基于表和字段生成业务对象、属性、关系候选。
5. 本体编辑：人工确认、修改、删除业务对象、属性和关系。
6. 语义映射：建立表到对象、字段到属性、字段值到状态的映射。
7. 规则配置：支持简单条件表达式和自然语言说明。
8. 规则执行：对选定业务对象实例执行校验和风险识别。
9. 语义解释：展示某条记录对应的业务对象、关系、状态和规则命中。
10. 语义 API：提供查询、解释、规则校验接口。
11. 审计记录：记录本体、映射、规则和执行结果的变化。

### 3.2 暂不包含

1. 多租户复杂计费。
2. 全量行业模板市场。
3. 完整 OWL 推理。
4. 拖拽式复杂流程引擎。
5. 对传统系统代码的自动改写。
6. 所有国产数据库适配。
7. 完整主数据治理平台能力。

## 4. 用户角色

### 4.1 平台管理员

负责数据源、系统配置、权限和审计。

### 4.2 本体工程师

负责领域本体、语义映射和规则模型的维护。

### 4.3 业务专家

负责确认业务概念、规则含义、状态流转和风险判断。

### 4.4 系统集成工程师

负责把语义 API 接入传统业务系统。

### 4.5 业务使用者

使用增强后的查询、解释、预警和操作建议能力。

## 5. 功能模块拆分

### 5.1 数据源与元数据模块

功能：

1. 新增数据库连接。
2. 测试连接。
3. 执行元数据扫描。
4. 展示表和字段列表。
5. 展示字段画像。

验收标准：

1. 能连接至少一种关系型数据库。
2. 能正确读取表、字段、主键、索引和注释。
3. 能展示字段样例和枚举候选。

### 5.2 本体建模模块

功能：

1. 创建领域本体。
2. 从元数据生成本体草案。
3. 编辑业务对象、属性、关系、状态。
4. 发布本体版本。

验收标准：

1. 能从合同管理数据库生成本体草案。
2. 能人工调整并发布一个本体版本。
3. 已发布版本不可直接修改。

### 5.3 语义映射模块

功能：

1. 表到业务对象映射。
2. 字段到属性映射。
3. 字段值到状态或枚举映射。
4. 关联字段到关系映射。
5. 映射确认和拒绝。

验收标准：

1. 每个已确认业务对象至少有一个数据来源。
2. 每个关键属性能追踪到来源字段。
3. 映射具备置信度、依据和审核状态。

### 5.4 规则与推理模块

功能：

1. 新增业务规则。
2. 配置规则适用对象。
3. 配置条件表达式。
4. 执行规则。
5. 输出命中结果和解释。

MVP 规则示例：

1. 合同金额必须大于 0。
2. 已生效合同必须存在签订日期。
3. 付款计划总额应等于合同金额。
4. 已到期未付款的付款计划产生逾期风险。
5. 客户状态为黑名单时禁止新签合同。

验收标准：

1. 至少支持 5 条合同管理规则。
2. 每条规则命中结果必须包含解释。
3. 每条解释能追踪到原始字段和值。

### 5.5 语义服务模块

功能：

1. 查询业务对象实例。
2. 查询实例语义解释。
3. 执行规则校验。
4. 查询风险结果。
5. 查询本体、映射和规则版本。

建议 API：

```http
GET /semantic/objects
GET /semantic/objects/{objectCode}/instances/{id}
GET /semantic/objects/{objectCode}/instances/{id}/explain
POST /semantic/objects/{objectCode}/instances/{id}/validate
GET /semantic/risks
```

验收标准：

1. 原业务系统或演示页面能调用语义解释接口。
2. API 返回结果包含业务名称、来源字段、规则命中和解释链。

## 6. 开发阶段

### 阶段 0：样例系统与数据准备

周期：1 周。

产出：

1. 合同管理样例数据库。
2. 20 到 50 条样例业务数据。
3. 初始业务规则清单。
4. 样例场景说明。

### 阶段 1：元数据接入

周期：1 到 2 周。

产出：

1. 数据源连接。
2. 元数据扫描。
3. 字段画像。
4. 表关系初步识别。

### 阶段 2：本体建模

周期：2 周。

产出：

1. 本体管理。
2. 业务对象编辑。
3. 属性和关系编辑。
4. 本体版本发布。

### 阶段 3：语义映射

周期：2 周。

产出：

1. 映射候选生成。
2. 映射确认界面。
3. 映射版本管理。
4. 映射影响分析雏形。

### 阶段 4：规则与推理

周期：2 到 3 周。

产出：

1. 规则配置。
2. 规则执行器。
3. 推理结果记录。
4. 解释链输出。

### 阶段 5：语义服务与演示闭环

周期：1 到 2 周。

产出：

1. 语义 API。
2. 演示页面或原系统接入样例。
3. 风险提示和操作建议。
4. MVP 验收报告。

## 7. 里程碑

| 里程碑 | 目标 | 成功标准 |
| --- | --- | --- |
| M1 | 接入传统数据库 | 能扫描并展示元数据 |
| M2 | 生成本体草案 | 能从表字段生成业务对象候选 |
| M3 | 发布本体版本 | 能人工确认并发布合同管理本体 |
| M4 | 建立语义映射 | 能解释表字段对应的业务含义 |
| M5 | 执行业务规则 | 能识别合同风险并输出解释 |
| M6 | 提供语义 API | 能被演示应用调用 |

## 8. 第一版数据模型建议

首版可以先以 PostgreSQL 存储平台配置和模型数据。

建议优先实现：

1. `data_source`。
2. `source_table`。
3. `source_column`。
4. `ontology`。
5. `business_object`。
6. `business_attribute`。
7. `business_relation`。
8. `semantic_mapping`。
9. `business_rule`。
10. `inference_result`。
11. `explanation_trace`。

## 9. 主要风险与控制

| 风险 | 表现 | 控制方式 |
| --- | --- | --- |
| 自动建模不准确 | 表名字段名不能表达真实业务 | AI 只生成候选，必须人工确认 |
| 规则过于复杂 | 首版规则引擎难以覆盖 | 先支持高频、确定、可解释规则 |
| 通用性过度设计 | 平台抽象迟迟不能落地 | 用合同管理闭环验证后再抽象 |
| 传统系统接入困难 | 权限、网络、数据库差异 | 首版用样例库和只读接入降低阻力 |
| 本体过于学术 | 业务人员无法维护 | 使用业务对象、属性、关系、规则等可理解概念 |

## 10. 下一步行动

建议下一步直接进入详细设计与原型开发准备：

1. 确认 MVP 行业场景，默认采用合同管理。
2. 设计合同管理样例数据库。
3. 设计平台自身数据库 schema。
4. 选择首版技术栈。
5. 搭建后端、前端和数据库工程骨架。
6. 实现数据源接入与元数据扫描。
