# ADR-0016 一致性契约随包发布

- 状态：Accepted
- 日期：2026-08-23

## Context

ROADMAP 阶段 D。扩展注册表自 ADR-0007 起就存在，每个扩展点必须满足的契约也写下来了——
写在 ADR 正文里，以及本仓库的测试文件里。

**两者第三方都拿不到。** 正文无法执行；`tests/` 不在 wheel 里。
于是集成方注册一个适配器后，**没有任何办法知道它是否正确**，
除非跑一次真实判定、然后去解读一个错误的结论。

更糟的是这让阶段 D 卡死。它被记为「阻塞于缺少第二个真实用例」，但这是循环论证：
**验证一个实现需要读我们的测试套件，就不会有第二个用例。**

### 真正会发生的 bug 不是崩溃，是不对称

解析器上最典型的错误：`list_ids()` 发出的 token 自己的 `fetch()` 不接受。
它能通过实现者想得到的每一个单元测试，然后在批量研判时**静默地什么都不返回**，
而单实例研判看起来完全正常。

这类 bug 靠「写文档要求实现者注意」是防不住的。

## Decision

### 契约作为可执行代码随包发布

`ontology_platform/conformance.py` 提供 5 个契约套件，
覆盖 5 个扩展点：实例解析器、数据源适配器、检索后端、嵌入模型、写回执行器。

### 不依赖 pytest

第三方项目可能不用 pytest，而**要求装一个测试框架才能验证插件，
对最需要这个检查的集成方恰好是一道门槛**。
每个套件返回结构化结果，可以从脚本、CI 步骤、pytest 测试或 `aletheia verify` 调用。

`ConformanceError` 继承 `AssertionError`，所以在 pytest 里直接
`report.raise_for_failures()` 就能得到正常的断言报告。

### 每一项检查都说明后果

失败信息不只说「哪条规则没过」，还说**违反它会导致什么**。

```
- list_ids() 的 token 能被 fetch() 接受: 以下 token 无法被 fetch() 接受: ['1-suffix']
  后果: 批量研判先列 token 再逐个 fetch。往返不闭合时批量研判静默地什么都不返回——
        这是自定义解析器最常见也最难发现的错误。
```

**不该让实现者去猜某条规则为什么重要。** 只说「哪条失败」会被绕过；
同时说清后果才会被修。

### 必需项与建议项分离

`required` 失败意味着正常运行下会产出错误结果；
`advisory` 意味着能用但少一项能力（非表数据源无法报告 `tables()`，
因此漂移检测覆盖不到它——但那是合理的实现，不该被拒绝）。

**混在一起会让报告无法用于「能不能上线」的判断**，而那正是集成方要它回答的问题。

### 契约套件本身不得崩溃

套件的全部目的是**报告**问题。对着一个残缺的实现抛异常，就等于没有报告。
因此每项检查都被包裹，异常被转成 finding。

### 内核自身的全部实现都跑同一套契约

4 种解析器、SQLite／CSV 适配器、BM25／嵌入检索后端、数据库写回执行器，
在 CI 中都跑契约。

**只对作者自己的例子成立的契约会漂移成「要求平台自己都不做的事」**，
那样第一个跑它的集成方拿到的失败是我们造成的。

### 反例测试是契约有效性的证明

一个只让我们自己的实现通过的契约可能是空的。
因此每一条属性都配一个**只违反该属性**的故意错误实现，并断言契约抓到它。

这在实现过程中已经产生了价值：原本有一项「结果可 JSON 序列化」检查，
写反例时才发现平台用 `default=str`，因此**任何对象都能序列化，该检查永不失败**。
真正的风险是另一回事：无法编码的值会被静默写成 `<object at 0x...>`，
审计留下的是内存地址而不是发生了什么。该项因此改为检查**如实往返**。

### `aletheia verify` 非零退出码

不合规时退出码为 1，因此不需要额外脚本就能作 CI 门禁。

### 契约不是 API 稳定承诺

注册表仍是实验性的（ADR-0007）。稳定的是**被要求的行为**，
不是要求它的函数签名。

## Alternatives considered

**把 `tests/` 打进 wheel。** 被否决：测试依赖 pytest 与 fixture，
且它们是为验证平台写的，不是为验证第三方实现写的——
集成方要从中挑出哪些适用于自己，本身就是负担。

**只在文档里写清契约。** 被否决：这是现状，且它没有产出任何第三方实现。
正文无法执行，也无法在 CI 中回归。

**用 `typing.Protocol` 做静态检查代替行为契约。** 被否决：
Protocol 能检查方法存在与签名，而真正会发生的错误是行为性的——
往返不闭合的解析器签名完全正确。

**要求第三方用 pytest 并提供 fixture。** 被否决：见上，门槛设错了地方。

**把所有检查都设为必需项。** 被否决：会排除合理的实现
（非表数据源无法报告 `tables()`），而实现者的合理反应是绕过契约。

## Consequences

正面：

- 第三方可以在上生产前自验实现，**阶段 D 的循环阻塞解除**
- 契约在 CI 中对内核自身实现回归，因此它不会漂移成空壳或不合理要求
- 失败信息带后果，使实现者倾向于修而不是绕
- `aletheia verify` 可直接作 CI 门禁

负面：

- 契约是行为性的，因此需要一个**活的被测对象**：数据源适配器契约必须连上
  含至少一表一行的真实数据源，无法离线验证
- 实例解析器与写回执行器的契约需要构造运行时／请求对象，因此只能在代码中调用，
  不能纯命令行完成
- 契约覆盖的是**内核依赖的属性**，不是实现的全部正确性：
  通过契约不等于实现没有 bug
- 每新增一个扩展点都要同时新增契约与反例测试，否则
  `test_every_suite_has_at_least_one_negative_test_in_this_file` 会失败——
  这是刻意的成本
