# ADR-0001 采用「库 + 脚手架 + 代码生成器」三仓库分发模型

- 状态：Accepted
- 日期：2026-08-21

## Context

Aletheia 目前是一个单仓库的可运行系统：后端 29 个模块、前端 React 应用、
一套示例业务系统。要把它交付给第三方使用，必须先回答「用户拿到的是什么」。

两种分发形态各有硬伤：

**纯库**（用户 pip install，自己搭应用）。上手门槛高。本项目的价值依赖一整条
链路——接入数据源、扫描元数据、审核映射、发布本体、配置规则、查看决策留痕。
光给库，用户要自己写完整的管理后台才能用起来，第一天就放弃。

**纯脚手架**（用户 fork 一份完整应用，直接改）。上手容易，升级无解。
用户 fork 后开始改我们的代码，内核出了安全修复（例如规则沙箱逃逸）时，
他们要手工 merge 一棵已经分叉很远的树。若依式脚手架在国内 B 端很流行，
代价正是「几乎无法升级」。

## Decision

三个仓库分工：

| 仓库 | 内容 | 用户如何对待 |
|---|---|---|
| `Aletheia-onto` | 内核库 | 依赖，pip 升级，不改 |
| `aletheia-scaffold` | 官方脚手架 | fork，随便改 |
| `aletheia-cli` | 脚手架初始化与代码生成 | 当工具用 |

内核以 PyPI 分包发布：`aletheia-core`（本体、规则、决策）、
`aletheia-web`（FastAPI 层）、`aletheia-admin`（管理界面）、
`aletheia-starter-*`（按场景预置的组合包）。

用户 fork 脚手架得到一个能跑的应用，业务定制写在自己的 fork 里；
内核通过版本号升级。可改的部分与要升级的部分从物理上分开。

## Alternatives considered

**单仓库 monorepo，用 extras 区分。** 拒绝理由：解决不了「用户改了内核代码」
这件事——只要内核和应用在同一棵树里，用户就会直接改内核。

**只发 Docker 镜像。** 拒绝理由：B 端要在自己的技术栈里做深度业务定制，
黑盒镜像不满足；且不解决二次开发的升级问题。

## Consequences

正面：内核可以独立演进并承诺语义化版本；脚手架可以大胆改动而不影响升级路径；
CLI 让「新建一个项目」变成一条命令。

负面：三个仓库的版本矩阵需要维护；跨仓库的破坏性变更要协调发布；
贡献者需要理解改动该落在哪个仓库。

**两个待决问题，现在无法回答，会影响本决定的落地方式：**

1. **隔离模型未定。** 多租户是「共享库带 tenant_id」「独立 schema」还是
   「独立库」尚未决定。这个选择渗透 31 张表与几乎所有查询，也决定
   `aletheia-core` 的数据访问层长什么样。在它定下来之前不应冻结分包边界。
2. **SPI 形状需要第二个真实用例。** 现在只有一个真实场景（合同管理）。
   仅凭一个用例反推的扩展点几乎必然是错的：它会把这个用例的偶然特征
   固化成 API。在拿到第二个真实用例之前，可以建内部注册表机制，
   但不对外承诺 SPI 稳定性。
