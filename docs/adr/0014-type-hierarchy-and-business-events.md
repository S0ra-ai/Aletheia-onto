# ADR-0014 类型层级与业务事件

- 状态：Accepted
- 日期：2026-08-23

## Context

ROADMAP 通用性 #6（类型层级）与 #9（Event／State 一等公民）。
两项合起来补完 `docs/02-核心元模型设计.md` 里画了但没建的部分：
对象、属性、关系、状态、规则都已实现，子类型与事件此前只存在于图上。

### #6 所有业务对象都是平级

真实 schema 里最常见的形状无法表达：

```
个人客户 / 企业客户  都是客户
定期合同 / 框架合同  都是合同
```

没有继承，一条适用于**所有**客户的规则要按子类型抄一遍。
这不只是重复：**副本会漂移**，漂移之后同一个业务问题会因为实例恰好属于哪个子类型
而得到两个不同答案。

### #9 有状态但没有历史

平台能回答：

| 问题 | 靠什么 |
|---|---|
| 这份合同现在是什么状态？ | State（工作流） |
| 这份合同现在合规吗？ | Rule（判定） |

但回答不了：

| 问题 | 缺什么 |
|---|---|
| 这份合同为什么变成现在这样？ | 事件历史 |
| 上个月有多少份合同被驳回？ | 事件作为数据 |
| 谁在什么时候改了金额？ | 带载荷的事件 |

**没有事件的状态是一张没有历史的快照**：平台能说什么是真的，
说不出发生过什么。而审计要的恰恰是后者。

## Decision

### 继承是沿声明链的确定性展开

**不是 DL 包含推理**（ADR-0005）。平台不推断 A 是否是 B 的子类型——那是声明的。
它做的是在判定时沿声明链展开：

- 子类型的规则集 = 自身规则 + 全部祖先规则
- 子类型的属性集 = 自身属性 + 全部祖先属性

两者都是沿声明链的一次遍历，同一个本体永远得到同一个展开结果，
这是判定可复现的前提。

### 覆盖必须显式声明，不靠同名推断

规则 code 在本体内唯一，因此子类型无法用同名遮蔽祖先规则。
覆盖改为声明：子类型作用域下的规则在 `overrides` 列里指明它取代哪条祖先规则。

**为什么不用同名推断。** 同名是有歧义的——两个团队可能各自取到同一个 code，
而推断会**静默停用其中一个团队的管控**。声明不会误触发。

覆盖声明会被校验：必须指向确实在上级链中的规则。
拼错会让作者以为祖先规则已停用，而它仍在阻断；
指向上级链外的规则则会停用一个毫无关系的类型上的管控。

**削弱不被禁止**——存在合法业务例外（国资交易对手豁免信用审查）。
被禁止的是**不可见地**削弱。

### 环在声明时拒绝，不在判定时

有环的层级没有well-defined的展开。在声明时拒绝并把环打印出来，
失败就落在造成它的人身上，而不是落在无法处置它的使用者身上。

若环因迁移或手工改库进入了存储，遍历按深度上限截断并告警——
拒绝评估整个实例会把一个错误声明变成一次停机。

### 聚合与派生属性同样沿层级继承

否则「客户合同总额」这类定义仍要按子类型抄一遍，回到 #6 的原始问题。
就近声明优先：一个名字必须解析到一个定义，否则规则看到哪一个取决于加载顺序。

### 事件是记录，绝不是触发器

记录事件不执行任何东西。这是刻意的：**能触发自动化的事件会让审计轨迹承载副作用**，
于是回放历史（回补、纠错、迁移）会重新执行业务动作。
自动化留在原处（`automation.py`），由决策驱动。

### 事件只追加

没有 update，没有 delete。记错的事件靠记录一条补偿事件来纠正——
这是账本的做法，也是唯一能让历史保持诚实的形状。
删除会留下一个无法解释自己如何形成的状态。

### 事件类型必须声明

否则「驳回」「拒绝」「rejected」会变成三个互不相关的事实，历史就不再可检索。

唯一例外是工作流镜像：工作流已经许可的流转，按定义就是一件合法发生过的事，
而已发布本体拒绝声明——若不豁免，**已发布本体上的每一次状态变更都会从历史中消失**。
该豁免插入的是一条事实记录，不是建模变更，所以发布不可变规则不适用于它。

### 载荷按声明字段校验，但只是提醒

缺字段记在事件上而不是拒绝：**一个停止发送某字段的老系统不该因此静默停止产生历史**，
而严格拒绝正会导致这个结果。多出的字段保留——丢弃集成方送来的数据
比存一个没人声明的字段更糟。

### 历史按来源时间排序

来源系统知道事情何时发生时，历史必须按那个时间排序。
按入库时间排序会把回补的数据顺序搞乱。

### 事件表的存在性用目录探测

靠捕获异常判断在 PostgreSQL 上是错的：一条失败语句会中止整个事务，
同一连接上后续每条命令都会以 `InFailedSqlTransaction` 失败。
这与 ADR-0004 记录的迁移陷阱完全相同。
**这个错误在本次实现中真实出现过**：解释接口里的 `try/except` 让
PostgreSQL 方言测试整条链路失败。

## Alternatives considered

**用判别列解析器表达子类型。** 被否决：它解决的是「哪些行属于这个对象」，
不解决「哪些规则适用于这个对象」。子类型各有自己的表时它完全无从下手。

**同名即覆盖。** 被否决：见上，会静默停用管控。

**禁止削弱祖先规则。** 被否决：存在合法业务例外，禁止会逼用户绕过平台。
要求的是可见，不是不可能。

**事件可触发自动化。** 被否决：回放历史会重新执行业务动作。

**允许删除或修改事件。** 被否决：会留下无法解释的状态。

**事件类型自由文本。** 被否决：可存但不可推理，同一件事会散成多个事实。

**沿用工作流历史表，不另建统一事件流。** 被否决：工作流历史按
`workflow_id` 组织，一个实例会有「每个子系统一条时间线」。
改为工作流流转镜像进统一事件流，实例只有一条时间线。

## Consequences

正面：

- 共性规则只写一次，判定结果不再依赖实例属于哪个子类型
- 判定结果标注规则来自哪个类型，运维知道该去哪里改
- 实例有统一时间线，解释能回答「为什么变成现在这样」
- 事件可计数，「上个月有多少份合同被驳回」不需要读文本
- 状态流转自动进入时间线，包括已发布本体上的流转

负面：

- 层级深度上限 16 层，更深需要重新建模
- 每次判定都要展开层级，深层级会增加一次判定的查询次数
- 事件表只追加，长期运行需要归档策略，平台不提供
- 覆盖需要显式声明，比同名覆盖多一步操作
- 事件不触发任何东西，需要「事件驱动动作」的场景仍要走自动化路径
