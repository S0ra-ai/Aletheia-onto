# ADR-0007 先开放扩展点，暂不承诺 API 稳定

- 状态：Accepted
- 日期：2026-08-21

## Context

项目目标包含「绝对的通用性」与「方便其他开发者二次开发」。当前状态与此冲突：
四处扩展点是硬编码的，第三方想加一种数据源、一个规则函数、一条路由策略或一种
写回通道，**唯一办法是 fork 并修改平台源码**——而 fork 之后就无法再升级内核。

| 位置 | 现状 |
|---|---|
| `adapters.py:74` `get_adapter()` | 硬编码 if/elif，三种类型 |
| `semantic_kernel.py:113` `ALLOWED_RULE_FUNCTIONS` | frozenset，5 个函数 |
| `access_policy.py:50` `RULES` | 模块级静态元组 |
| `automation.py` 写回执行器 | 只支持 HTTP/HTTPS |

同时 [ADR-0001](0001-three-repo-distribution.md) 与 ROADMAP 阶段 D 记录了一条
相反方向的约束：**在拿到第二个真实用例之前不应冻结 SPI**，否则会把第一个用例的
偶然特征固化成永久 API。

这两件事看似对立，实际上混淆了两个独立的问题。

## Decision

把「**能否扩展**」与「**接口是否稳定**」分开处理：

1. **立刻开放扩展能力。** 四处硬编码改为运行时注册表，第三方无需 fork
   即可注册自己的实现。这解决二次开发的实际障碍。
2. **暂不承诺接口稳定。** 在 1.0 之前，扩展点的签名可能随第二、第三个真实用例
   调整。破坏性变更会记入 CHANGELOG 并在 ADR 中说明理由。
3. **用一致性测试套件替代口头承诺。** 第三方实现跑这套测试即可自证合规；
   我们改签名时，这套测试同时暴露所有受影响的实现点。

换言之：**开放，但标注版本期望。** 这比两个极端都好——
锁死扩展点会逼人 fork（然后无法升级），过早冻结 API 会锁死我们自己的演进空间。

## Alternatives considered

**等第二个用例再开放。** 拒绝理由：这期间任何想扩展的开发者只能 fork，
而 fork 正是三仓库模型要避免的结果。且第二个用例可能恰恰来自某个想扩展的
开发者——不开放就等不到它。

**开放并承诺稳定。** 拒绝理由：现在只有一个真实场景（合同管理）。据此冻结的
`InstanceResolver` 形状几乎必然是错的，而承诺过的 API 撤不回来。

**只提供文档说明如何 fork。** 拒绝理由：等于放弃「可升级」这一核心卖点。

## Consequences

正面：第三方今天就能接 Oracle、达梦、人大金仓，或注册自定义规则函数，
不动平台代码。扩展点从「设计意图」变成「可执行的机制」。

负面：0.x 期间升级内核可能需要调整第三方实现。必须在 README 与 CONTRIBUTING
中明确说明这一点，不能让人误以为签名已稳定。

负面：注册表引入间接层，读代码时「谁注册了什么」不如 if/elif 直观。
以内置实现在导入时自注册、并提供 `list_*` 内省接口来缓解。

## 稳定性标记约定

| 标记 | 含义 |
|---|---|
| 🟢 稳定 | 1.0 后遵循语义化版本 |
| 🟡 实验性 | 可能在小版本间变更，变更记入 CHANGELOG |
| 🔴 内部 | 不面向第三方，随时可变 |

**当前所有扩展点均为 🟡 实验性。** 首个 🟢 需要至少两个独立真实用例验证形状。
