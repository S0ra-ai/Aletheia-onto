# ADR-0012 跨对象聚合与关系语义

- 状态：Accepted
- 日期：2026-08-23

## Context

ROADMAP 通用性 #4（关系表达力）与 #5（跨对象规则与聚合）。两者都源于同一个缺口：
**规则只能看见一个实例**，而关系只是外键的复述。

### #5 规则的视野只有一行

规则绑定单个 `scope_object_code`，表达式只能读到被评估实例与其直接关联行。
B 端最先提出的需求恰好都是关于**一组**实例的：

| 需求 | 为何做不到 |
|---|---|
| 客户所有合同总额不得超过其信用额度 | 只能看到当前这一份合同 |
| 同一设备的未关闭工单不得超过 3 个 | 需要跨兄弟实例计数 |
| 本月该客户的退款次数不得超过 2 次 | 同上 |

### #4 每个外键都被归结为同一个常量

`relation_type` 恒为 `"references"`。这不是关系模型，只是外键的另一种写法。
缺失的三件事，都是业务人员描述领域时的第一句话：

| 缺失 | 后果 |
|---|---|
| 基数 | 无法区分「一条关联行」与「一组关联行」 |
| 强弱 | 付款计划离开合同即垃圾，合同离开可选销售代表却无妨；删除与级联全靠这个区分 |
| 多对多 | 中间表被建成业务对象，每条规则都要绕过一个业务上不存在的行 |

其中「基数」的后果不只是不便，而是**错误判定**：一对一子表若按集合注入，
`contract_signature.status != 'void'` 求值为 `[False]`——非空列表为真，
于是按常规写法写出的规则会静默通过。

## Decision

### 聚合是声明的数据，不是规则里的内联查询

`cross_object_aggregate` 存放具名聚合：从被评估实例取一个分组值，
在目标对象的匹配行上施加函数，结果以普通数字注入沙箱。

```
customer_active_total = sum(contracts.total_amount)
                        where contracts.customer_id = 本实例.customer_id 且 status = 'active'
```

规则因此保持简单：`customer_active_total <= 1000`。

**为什么不允许在表达式里直接写 join。** 「为什么」的答案必须是一份运维可以读、
可以审阅、可以随语义资产导出的定义，而不是一句没人审过的查询。这与 ADR-0011
把解析器配置存成数据的理由相同。

### 聚合算不出来时让规则失败，而不是当作 0

分组值为空、目标列含非数值、`min/max/avg` 无可用数据——这些情形不产生数值。
只有成功计算的聚合进入沙箱，被引用而缺失的名字触发 `NameError`，
由内核的 fail-closed 处理转为「未通过 + 原因」。

注入 `None` 或 0 会让 `x <= limit` 静默成立，那正是 ADR-0002 要防的失败模式。
`sum` 的空集是 0，因为空集之和确实是 0；`avg` 的空集无定义，所以报错。

### 聚合有行数上限，且触顶必须上报

每次评估都会执行该对象的全部聚合，无界聚合会让每次判定退化为全表扫描。
`MAX_AGGREGATION_ROWS` 封顶，触顶会在结果里标记而非静默截断——
静默截断出来的数字看起来完全正常，却是错的。

读行后在 Python 内计算，而不是下推聚合 SQL。取舍是明确的：
**牺牲下推性能，换三方言行为完全一致**，并沿用适配层已有的引号处理。

### 关系语义只从声明结构推断，绝不看数据分布

| 结构 | 基数 | 类型 |
|---|---|---|
| 外键构成子表全部主键 | 一对一 | 组成 |
| 外键是复合主键的一部分 | 多对一 | 组成 |
| 外键非空且不在主键内 | 多对一 | 聚合 |
| 外键可空 | 多对一（可选） | 关联 |
| 主键恰由两个外键组成 | 多对多 | 关联 |

从采样推断出的关系会在数据变化时改变含义，引用它的判定就不可复现（ADR-0005）。
「组成」意味着身份依赖：父键是子身份的一部分，这是关于 schema 的事实，不是猜测。

每条关系都存 `inference_reason`。**没有依据的分类无法被审阅**——
运维要纠正一条生成的关系，必须先知道它为何被这样分类。

### 中间表折叠成多对多，但对象保留

中间表常自带属性（`role`、`valid_from`、`weight`），删掉对象就丢了这些属性。
因此两个视图并存：供规则与问答使用的直接多对多，以及承载属性的中间表对象。

判定标准取严：主键必须恰为两个外键且指向不同表。带代理主键 `id` 的两外键表
**不**判为中间表——它有自己的身份，通常业务真的在谈它（订单行、选课记录）。
这里的代价不对称：错误折叠会让一个真实对象从模型中彻底消失，
而漏判只是多留一跳，建模人员可以手工合并。

### 升级默认值取最弱分类

既有 `business_relation` 行没有这些列，迁移默认值为
`many_to_one` / `association` / 可选。这是最弱的分类，因此升级不会让任何
原本不级联的链接变成级联。

## Alternatives considered

**在规则表达式里开放 join 或子查询。** 被否决：表达力最强，可审阅性最差。
每条规则都会变成一段没人审过的 SQL，「为什么」也就答不出来。

**从数据分布推断基数**（如「该列每个值平均出现 1.02 次，判为一对一」）。
被否决：结论随数据变化，判定不可复现。

**把聚合下推为 SQL `sum()`／`count()`。** 被否决：三方言的 NULL 语义、
类型提升与引号规则各不相同，而这条路径产出合规判定。行数上限是为一致性付的价。

**删除中间表对象。** 被否决：会丢失中间表自身的属性。

**把基数编码进 `relation_type` 字符串**（如 `"references:many-to-one"`）。
被否决：既有读取方与导出会拿到无法解析的值。基数单列存放。

## Consequences

正面：

- 「客户所有合同总额超限」这类需求可以在不写代码的前提下表达
- 一对一子表注入为单行，按常规写法写出的规则不再静默通过
- 多对多可直接穿越，规则不必经过中间表
- 关系带基数与强弱后，图谱视图与解释可以区分单个关联对象和集合

负面：

- 聚合在 Python 内计算，大表上比下推慢，靠行数上限兜住
- 每次评估都会执行该对象的全部聚合，聚合定义过多会拖慢判定
- 关系分类依赖 schema 声明质量：不写外键、不写 NOT NULL 的库只能得到最弱分类
- 跨源聚合仍不支持，阻塞于跨源实体消解
