# ADR-0009 文档知识层锚定本体，不做独立 RAG 模块

- 状态：Accepted
- 日期：2026-08-21

## Context

项目对外声称的目标形态是这样一句客服回答：

> 「订单 A123 不满足退款条件，因签收已超 15 天（规则 `refund_window_check`），
> 依据《售后政策》第 3.2 条。」

三段来源不同：「超 15 天」来自结构化查询，「不满足」来自规则引擎，
**「第 3.2 条」来自文档检索**。

前两段已实现。第三段此前完全没有——`embedding`、`vector`、`chunk`、`rerank`
在 32 个后端模块中零命中。也就是说护城河只成立三分之二：
能给出结论与规则，但给不出条款依据。

这是当前实现与产品定位之间最大的单一缺口。

## Decision

补齐文档检索，但**必须锚定到本体对象，不做成独立的 RAG 模块**。

### 锚定的含义

每个知识条目（chunk）必须声明它服务于哪些本体对象或规则：

| 字段 | 作用 |
|---|---|
| `object_code` | 该条目解释哪个业务对象 |
| `rule_code` | 该条目是哪条规则的文字依据 |
| `citation` | 人类可引用的定位，如「第 3.2 条」 |

检索时先按当前研判涉及的对象与规则收窄候选，再做相似度排序。
**这与「先全库检索再看看命中了什么」是相反的方向。**

### 为什么不做独立 RAG

如果做成一个通用的「文档问答」模块，本项目就退化为 Dify／FastGPT 的同类产品，
而检索精度不是我们的优势，也明确列在 Non-Goals 里。

更实质的原因：**独立 RAG 给不出可核验的引用。** 通用 RAG 返回「最相似的三段文本」，
它们与判定结论之间没有可指认的关系——无法回答「这段文字凭什么支持这个结论」。
锚定到规则的知识条目可以：`refund_window_check` 这条规则的文字依据就是第 3.2 条，
这个关联是建模时声明的，不是检索时猜的。

### 治理

知识条目沿用现有治理流程（`pending` / `confirmed` + 发布门禁），**不自动上线**。
理由与 ADR-0002、ADR-0008 一致：自动切分的结果不能直接当作生产真值。
一段被错误切分的合同条款，如果直接进入判定依据，产生的是「看起来有据可查
但依据是错的」——比没有依据更危险。

### 检索后端与嵌入模型均为 SPI

默认实现刻意选择**零外部依赖**的方案：

- 嵌入：基于字符 n-gram 的哈希向量（确定性，无需模型服务）
- 检索：BM25 词频排序 + 本体过滤

这不是最优检索质量，而是保证「clone 下来就能跑」。追求质量的部署通过
`register_embedding_model()` / `register_retrieval_backend()` 接入
pgvector、Milvus、OpenAI embeddings 等，无需 fork（ADR-0007）。

## Alternatives considered

**直接内置 pgvector 或 Milvus。** 拒绝理由：违反「无外部服务即可运行」这一
快速开始承诺，且把一个部署选择固化成框架依赖。作为 SPI 实现更合适。

**内置 OpenAI embeddings。** 拒绝理由：未配置密钥时能力消失。
模型层已有的回退策略（`model_client.py` 未配置密钥时回退本地启发式）
说明这条路走得通，检索也照此办理。

**让知识条目自由浮动，检索时再关联对象。** 拒绝理由：这就是独立 RAG。
关联关系必须是建模时声明并经审核的，否则无法作为判定依据。

**跳过治理，切分后直接可检索。** 拒绝理由：见上文，错误依据比无依据更危险。

## Consequences

正面：护城河那句话三段齐全，可以端到端演示。文档依据与规则的关联可审计。

负面：知识条目需要人工确认，接入成本高于「上传即可问」的 RAG 产品。
这是与可核验性绑定的必然代价。

负面：默认检索质量弱于专业向量库。**README 必须如实说明这一点**，
不能让读者以为内置实现可与 pgvector 相提并论。

负面：切分策略对中文合同类文档的效果依赖标点与条款编号，
对格式混乱的扫描件 OCR 结果效果差。已在限制中记录。
