# ADR-0008 实例键抽象与值域映射

- 状态：Accepted
- 日期：2026-08-21

## Context

两个约束长期把 `business_object` 限制为「表的镜像」：

1. **复合主键完全不支持。** `ontology.py`、`semantic_kernel.py` 三处显式
   `raise ValueError("当前原型不支持复合主键")`。这排除了连接表、版本化记录、
   按判别列分区的历史表——真实遗留库中占比很大的一类。
2. **值域只有原始码。** `status='A'` 无法表达为「生效中」，
   规则只能写成 `status == 'A'`，而这条规则只有记得码表的人才能复核。

## Decision

### 实例键（InstanceKey）

把此前混在一起的三件事分开：

| 概念 | 含义 | 来源 |
|---|---|---|
| 定义 | 哪些列标识一个实例 | `source_table.primary_key` |
| 值 | 某个实例的具体键值 | 数据行 |
| 标识串（token） | API 与决策记录中使用的字符串 | 由前两者派生 |

**单列键的 token 保持为裸值**，复合键为 `col=value;col=value`（百分号编码）。
这个不对称是刻意的：既有的 `decision_record`、`audit_log`、API 调用方全部
存着裸值，改成统一格式会让历史留痕无法关联。

### 为什么用百分号编码而非自定义转义

最初实现了反斜杠转义，随后被对抗性往返测试打出两个真实缺陷：

- 值中含 `=` 时，列/值切分错位
- 值中含字面反斜杠时，反转义过程把它吞掉

`quote`/`unquote` 是严格互逆的，且天然处理分隔符、反斜杠与非 ASCII——
而业务键三者都会出现（合同编号带中文、备注带分号）。教训是：
**分隔符转义看起来简单，实际是容易写错的一类代码,不该手写。**

### 值域映射（value_to_state）

作为 `semantic_mapping` 的第三种 `mapping_type`，因此**自动继承既有治理流程**：
生成的候选是 `pending`，只有 `confirmed` 才生效。这一点是硬要求——
未经复核的猜测绝不能改变合规判定结论。

**最关键的设计约束是向后兼容：** 新增一条映射不得改变已写规则的含义。
否则某人整理了一次码表，全平台的判定结论就会静默漂移。

`MappedValue` 是 `str` 子类，同时等于原始码与语义状态名，
于是 `status == 'A'` 与 `status == '生效中'` 对同一单元格都为真。
继承 `str` 使既有的比较、`in`、字符串方法、JSON 序列化全部照常工作。

## Alternatives considered

**用整数序号或哈希作为复合键 token。** 拒绝理由：不可读，且需要一张映射表
才能从留痕反查实例,审计时无法直接指认。

**在规则求值前把状态名替换回原始码（文本替换）。** 拒绝理由：
字符串替换会误伤同名的普通字符串字面量,且无法区分「这个字符串是状态名」
还是「恰好长得像状态名的备注」。

**用独立的 `value_mapping` 表。** 拒绝理由：会与 `semantic_mapping`
的审核、发布门禁、版本冻结逻辑重复一遍。复用 mapping_type 则零成本继承。

**让映射立即生效（不走 pending）。** 拒绝理由：与 ADR-0002 的取舍一致——
自动生成的东西不能直接当作生产真值。

## Consequences

正面：连接表与版本化表可以建模了。规则能写成业务语言而不是魔法值。
两项都有测试覆盖，并在三种方言上验证。

负面：`MappedValue` 的双向等值是一处「聪明」的实现，读代码时需要理解
为什么 `==` 会对两个不同字符串都为真。已在类 docstring 中写明理由。

负面：复合键 token 出现在 URL 中时较长且带百分号编码，可读性不如裸值。

**仍未实现（避免声称过头）：**

- 一个对象仍然只能绑定一张表（`source_table_id` 单外键）。
  实例键解除了「单列主键」假设，但没有解除「单表」假设——
  多表 join、判别列分区、跨源仍属通用性 #1 的后续工作。
- 值域映射只作用于规则求值上下文,尚未用于问答回答的状态名渲染。
