# ADR-0010 上下文对象取代全局单例

- 状态：Accepted
- 日期：2026-08-22

## Context

`database.py` 的 `_platform_adapter` 是模块级全局单例，因此**一个进程只能持有
一套平台配置**。这堵死三件事：

1. **多租户**（[ADR-0006](0006-tenant-isolation-model.md)）。「每租户一个 schema」
   要求连接与租户绑定，单个全局变量无法表达这件事。
2. **测试与嵌入**。同一进程内验证两种方言、或在一个应用里嵌入两次内核，都做不到。
3. **请求级隔离**。FastAPI 在线程池上并发处理请求，全局变量意味着
   一个请求的配置会影响另一个请求。

同时存在一个规模问题：**156 处函数签名**接收 `platform_db: Path | str`。
一次性全部重写会产生极大的 diff，而其失效模式是「漏改一处」——
在租户语境下，漏改一处等于跨租户数据访问。

## Decision

引入 `PlatformContext`，承载原先全局变量持有的内容（方言、连接串、缓存的适配器），
外加多租户将需要的租户标识与 schema。

**关键决定是以「放宽」而非「替换」的方式落地：**

`resolve_context()` 接受四种形态——上下文对象、路径、字符串、空值——
因此 `connect()` 与 `initialize_platform_db()` 在接受路径的同一位置也接受上下文。
156 处既有签名**一行不改即可继续工作**，新代码显式传上下文。

迁移因此是渐进且可审查的：模块在被触碰时改为显式上下文，两种风格同期有效。
`use_context()` 标记出「请求级上下文绑定」的接缝。

### 线程局部而非全局

`use_context()` 绑定到线程局部而非全局。理由直接来自被替换的缺陷：
FastAPI 并发处理请求，若绑定是全局的，一个请求 pin 的租户会泄漏到另一个请求。

### 适配器缓存加锁

`PlatformContext.adapter` 用锁保护惰性创建。两个线程同时触碰一个新上下文时，
否则会各自建一个适配器，其中一个被静默丢弃——连同它持有的任何状态。

### 保留旧全局

`configure_platform_db()` 仍然存在（应用启动已在调用它），现在改为设置默认*上下文*，
并让 `_platform_adapter` 指向**同一个适配器实例**。这样即使有调用方直接读旧全局，
也不会落到与上下文路径不同的连接上。

## Alternatives considered

**一次性重写 156 处签名。** 拒绝理由：diff 过大，且失效模式是「漏改一处」，
而在租户语境下这等于跨租户泄漏。放宽式迁移让每一步都可独立验证。

**用 `contextvars` 而非 `threading.local`。** 部分保留。`contextvars` 对
async 更正确，但平台当前的数据访问是同步的，且 FastAPI 的同步端点跑在线程池上，
线程局部与实际执行模型匹配。若将来引入 async 数据访问，这一处需要重新评估。

**把租户作为参数传给每个函数。** 拒绝理由：这正是 156 处签名问题的翻版，
只是把 `platform_db` 换成 `platform_db, tenant`。

## Consequences

正面：同进程内多实例、多方言、多租户成为可能。请求级绑定不再互相干扰。
已验证：两个 SQLite 实例数据互不可见、SQLite 默认上下文与真实 PostgreSQL 上下文
并存、线程绑定不泄漏、8 线程竞争下只创建一个适配器。

负面：`resolve_context()` 接受四种输入，这是刻意的兼容代价，但读代码时
「这个参数到底是什么」不如单一类型直观。已在 docstring 中写明每种形态的含义。

负面：**仍不是连接池。** 每次 `connect()` 新建连接，与此前一致。
连接池仍记在 `docs/architecture-debt.md`。

**仍未完成（避免声称过头）：**

- 156 处 `platform_db: Path | str` 签名**尚未改为上下文对象**，只是现在能接受它。
  逐模块迁移是后续工作。
- **多租户本身仍未实现。** 本 ADR 只移除了它的阻塞项；`tenant` 字段目前恒为
  `default`，31 张表仍无 `tenant_id`。README 能力矩阵继续标注 📋。
- schema 路由（`PlatformContext.schema`）字段已存在但**尚未被适配器使用**。
