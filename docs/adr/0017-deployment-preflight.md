# ADR-0017 部署前自检与私有化部署形态

- 状态：Accepted
- 日期：2026-08-23

## Context

ROADMAP 阶段 G。`aletheia doctor` 回答的是「配好了吗」，那是开发期问题。
**没有任何东西回答「这套配置放到生产上安全吗」**，而这个问题只在服务开始接收请求之前
还便宜。

仓库里也没有任何部署产物：没有镜像、没有编排、没有配置范例。
于是每个部署方各自摸索，而他们摸索出的第一版通常带着开发默认值。

### 每一种误配置都是静默的

这是关键。平台会正常启动、正常服务、看起来健康：

| 误配置 | 实际发生什么 |
|---|---|
| `ONTOLOGY_AUTH_DISABLED=1` 残留 | **整套 API 无需令牌即可访问，包括对遗留系统的写回** |
| CORS 为 `*` | 任意站点都能携带用户凭据驱动本 API |
| CORS 仍是 localhost | 真实前端被拦，随后有人会用 `*` 绕过 |
| 未设管理员口令 | 随机口令只打印一次，容器日志轮转后没人能登录 |
| SQLite 配多工作进程 | 写入串行化，高并发下表现为**间歇性超时**而非明显配置错误 |
| 平台库文件 644 | 该文件保存全部数据源连接串，等同凭据存储 |

没有一项会在启动时报错。

## Decision

### 拒绝，而不是警告

启动日志里的警告只会被读一次——被那个搭建服务的人，此后再也不会。
`aletheia preflight` 阻断项存在时退出码非 0，**让部署流水线停下**，
而那是「认证被关闭了」仍然容易修的最后一刻。

### `serve` 在非本机监听时强制自检

没人会记得单独跑一个命令，而唯一真正需要它的那次部署，
恰好就是 `ONTOLOGY_AUTH_DISABLED=1` 忘了删的那次。

绑定 loopback 时不检查：**本地开发必须保持无摩擦，否则这个检查会被全局关掉。**
判据是「是否可从网络访问」，因为那决定了阻断项是理论风险还是可利用风险。

### 阻断项与警告项分离

与一致性契约同一个理由（ADR-0016）：
把「这可被利用」和「这会很慢」混在一起，报告就无法用于「能不能上线」的判断。

单节点 SQLite 评估部署是**合理**的形态。拒绝它会让人索性跳过整个检查。

### 每一项失败都给出处理办法

只报「哪条没过」而不说该设什么，是一种会被学会忽略的检查。

### 读环境变量，不读配置文件

进程实际会用的是环境。**配置文件正确而环境变量覆盖了它**，
正是这个自检要抓的那类失败。

### 检查项清单由实现派生

`describe_checks()` 跑一次真实检查来产出清单，而不是手工维护一份——
手工清单会漂移，而**一份高估了「已验证内容」的清单比没有清单更糟**：
使用者会信任一个并不存在的检查。

它也**不修改环境**：一个改变了进程配置的 describe 调用本身就是个陷阱。

### 镜像：两阶段、非 root、无内置凭据

两阶段不是为了体积。**一个能拉取并编译任意包的运行时容器，
是从「一次代码执行」到「持久化后门」最短的路径。**

非 root 运行，因为平台库保存全部数据源连接串——
以 root 运行意味着一次容器逃逸即交出所有凭据。

镜像不内置凭据、也不预置数据库：内置一份 SQLite 会让所有部署共用同一份初始数据，
而那份数据里正是数据源连接串。

### 编排：`:?` 强制设置，数据库端口不外发

`${VAR:?}` 让 compose 在未设置时直接失败。
**参考编排里的默认口令就是会到生产上的口令。**

数据库端口不映射到宿主：平台通过 compose 网络访问它，
而暴露 5432 会让凭据存储直接可达。

### `.env.example` 不带任何可用值

带着可用凭据的范例文件，最终总会被原样部署。
而 `aletheia preflight` 恰好会拦下 `change-me` 这类占位值——两道防线彼此补充。

## Alternatives considered

**只在文档里列出生产配置清单。** 被否决：这等于把检查交给记忆力，
而失败是静默的——没人会发现自己漏了一项。

**启动时打印警告而不阻断。** 被否决：警告只会被读一次。

**所有检查都设为阻断项。** 被否决：会拒绝合理的单节点 SQLite 部署，
而使用者的合理反应是跳过整个检查。

**`serve` 无条件强制自检。** 被否决：本地开发会变得处处摩擦，
然后这个检查会被全局关掉——包括生产。

**镜像内置一个已初始化的 SQLite 以便开箱即用。** 被否决：
所有部署共用同一份初始数据，而那份数据保存数据源连接串。

**在自检里做端口扫描、备份检查等基础设施检查。** 被否决：
那些有成熟工具，而一个半成品版本会诱使别人把它当完整方案来信任。

## Consequences

正面：

- 免鉴权暴露这类最危险的误配置在流水线阶段被拦下，而不是在事故中被发现
- 部署方拿到可运行的最小生产形态，而不是从开发默认值开始摸索
- 每项失败带处理办法，因此倾向于被修而不是被绕
- 检查项清单由实现派生，不会漂移成过度承诺

负面：

- 自检读**当前进程**的环境，因此在与实际运行环境不同的机器上跑意义有限
- 只覆盖平台自身的配置：TLS 终止、网络策略、备份、密钥轮转均在范围外，
  且刻意不做半成品版本
- 通过自检**不等于部署安全**，只等于没有本平台已知的那几类误配置
- 参考编排是单节点的：多副本、滚动升级、外部密钥管理需要部署方自行扩展
- `--skip-preflight` 存在，因此它可以被绕过——这是刻意的，
  一个无法绕过的门禁会被整体禁用
