# ADR-0006 多租户隔离：独立 schema 起步 + 关键表带 tenant_id

- 状态：Accepted
- 日期：2026-08-21
- 决策者：项目所有者

## Context

平台目前没有任何租户概念：31 张表零 `tenant_id`，`database.py:20` 的
`_platform_adapter` 是模块级全局单例，一个进程只能持有一套配置。

这个选择必须在写任何多租户代码之前定下来，因为它渗透 31 张表与几乎所有查询。
等到写了一半再改，等于把所有查询重写一遍。

三个候选：

| 方案 | 隔离强度 | 运维成本 | 跨租户查询 |
|---|---|---|---|
| 共享表 + `tenant_id` | 弱，依赖每条 WHERE 不写漏 | 低 | 容易 |
| 独立 schema | 中，数据库层强制 | 中 | 需跨 schema |
| 独立库 | 强 | 高，连接数与迁移成本随租户线性增长 | 困难 |

共享表方案的失效模式很具体：**一条忘写 `where tenant_id = ?` 的查询就是一次
跨租户数据泄漏**，而且这类漏写在测试里往往看不出来——单租户测试数据下，
漏写过滤条件的查询返回结果完全正确。

## Decision

**独立 schema 起步 + 关键表带 `tenant_id` 双保险。**

1. 每个租户一个 schema，由数据库层强制隔离。连接建立时设定 search_path
   （PostgreSQL）或 database（MySQL）。
2. **同时**在关键表上保留 `tenant_id` 列并加约束。即便某条查询漏写了过滤，
   数据也仍在正确的 schema 里；反之若 schema 路由出错，`tenant_id` 校验会
   把错误变成一次可见的失败而不是静默的越界读取。
3. SQLite 无 schema 概念，退化为「一个租户一个库文件」，保持开发体验不变。

两层的意义在于它们的失效模式不重叠：schema 防漏写过滤，`tenant_id` 防路由错误。
任一单层出问题，另一层仍然拦得住。

## Alternatives considered

**仅共享表 + `tenant_id`。** 拒绝理由：唯一的防线是「每条查询都记得加过滤」，
而本项目有 98 个端点和大量动态构造的查询。这是把正确性押在纪律上。

**仅独立库。** 拒绝理由：连接池、迁移执行、备份策略的复杂度随租户数线性增长。
对尚无第一个付费租户的项目，这是提前支付的成本。保留为后续可选的部署形态——
独立 schema 的抽象足以在之后升级到独立库，反之则不然。

## Consequences

正面：隔离由数据库强制，不依赖应用层纪律。迁移路径清晰——独立 schema 之上
可以再演进到独立库，因为两者都要求「连接与租户绑定」这一抽象。

负面：跨租户的运营统计需要显式遍历 schema。迁移要对每个 schema 执行一遍。

**前置依赖：** 必须先消除 `_platform_adapter` 全局单例，改为携带连接、配置与
租户标识的上下文对象。这是 ROADMAP 阶段 C 的工作，现在成为阶段 B 的硬前置。

## 实施顺序

本 ADR 只固定方向，不代表已实现。当前状态仍是**单租户、零 tenant_id**。
顺序为：上下文对象 → schema 路由 → 关键表 `tenant_id` → 检索期过滤 →
修 `permission_policy` 缺本体维度缺陷。
