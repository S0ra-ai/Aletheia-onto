# ADR-0018 跨源实体消解：匹配是声明的

- 状态：Accepted
- 日期：2026-08-23

## Context

ROADMAP 通用性清单上最后一项结构性空白。一个业务对象此前只能绑一个数据源，
于是这一类需求完全无法表达——而它在 B 端是常态：

| 场景 | 主源 | 副源 | 对应键 |
|---|---|---|---|
| 客户主数据与合同 | CRM | ERP | 税号 |
| 设备台账与运行数据 | 资产系统 | SCADA | 设备编号 |
| 人员与权限 | HR | AD | 工号 |

此前 ROADMAP 把它记为「阻塞于连接管理」，那个判断是错的。
真正的前置问题是：**CRM 的第 42 行和 ERP 的第 7 行是同一个客户吗。**

那个判断会进入判定链。若它不可核验，基于它的每个结论都不可解释——
「为什么这份合同被阻断」的答案会变成「因为我们认为这两行是同一个客户」，
而没人能审阅「我们认为」。

## Decision

### 匹配是声明的，绝不是相似度推断的

| 做法 | 是否采用 | 理由 |
|---|:--:|---|
| 声明「CRM.customer.tax_id ↔ ERP.client.taxpayer_no」 | ✅ | 可审阅、可导出、每次得出同一结果 |
| 字符串相似度、编辑距离、模糊匹配 | ❌ | 阈值变一点，判定结论就变 |
| 机器学习实体链接 | ❌ | 无法说出「为什么这两行是同一个」 |
| 多键组合（税号 + 名称都相等） | ✅ | 仍是精确相等，只是条件更严 |

这与关系语义（ADR-0012）、CSV 不推断外键（ADR-0015）是同一条原则：
**结构必须是声明的。** 从巧合或相似度推出的对应关系，其上的判定无法解释。

规范化只做**确定性**的部分：去空白、统一大小写、统一转字符串
（跨源时同一个业务键常有不同存储类型，CRM 存 varchar 而 ERP 存 bigint，
按原类型比较会一个都匹配不上）。不做同义词替换、不做拼写纠正——
那些会让匹配结果随词表变化。

### 一对多是错误，不是「需要挑一个」

跨源匹配最危险的失败不是找不到，而是**找到了多个**。
若副源有两行税号相同，平台**拒绝**而不是挑第一行——
挑一行会让判定作用在一条任意选中的记录上，而结果看起来完全正常。

确实允许取任一行的场景存在，但那必须**声明**（`requireUnique=False`），
不能是默认。

### 冲突被标记，不让某一侧静默胜出

两侧对同名字段给出不同值时（CRM 说信用额度 100 万，ERP 说 50 万），
默认标记为冲突。

`ConflictingValue` 刻意**不是** str 或 float 的子类：跨源冲突不该能参与比较。
规则引用它会抛 TypeError，由 fail-closed 转为「未通过 + 原因」——
这正是应有的结果，**因为没人能说清该用哪一侧的值**（ADR-0002）。

允许声明取哪一侧，但选择本身会留痕，否则事后无法解释用了哪个值。

### 主源决定身份

一个跨源对象有且只有一个主源：实例 id 来自它。
否则同一个业务实例会有两个 token，而判定记录、审计行与 URL 里会各存一个。

### 匹配失败不注入任何字段

注入 None 会让 `erp_credit_limit > 0` 求值为假，与真实业务违规无法区分。
缺席则触发 NameError，由 fail-closed 转为「未通过 + 原因」。

### 跨源聚合复用同一条原则

`AggregateSpec.target_data_source_id` 让「这个客户在 ERP 里的订单总额」可表达。
行仍按声明列上的相等条件匹配，因此跨源聚合与同源聚合一样可解释。

默认 0 表示本源，等于既有行为——**升级不改变任何已存聚合的结果**。

### 副源不可达时报错，绝不回落到本源

读**错的表**会静默产出一个看起来合理的数字。

### `SchemaBundle` 需要加列能力

实现跨源聚合时发现的真实缺陷：`SchemaBundle` 只做
`create table if not exists`，而它对已存在的表什么都不做。
于是新增字段**只对全新部署生效**——功能在开发机上能用、升级后不能用，
且不会有任何报错。

因此给它加了 `ColumnAddition`：先查目录再执行 DDL，
因此幂等且不依赖驱动的错误文本（捕获异常会在 PostgreSQL 上中止事务，ADR-0004）。

## Alternatives considered

**用相似度或 ML 做实体链接。** 被否决：判定结论会随阈值与模型变化，
且无法回答「为什么这两行是同一个」。这不是能力不足，是与可核验性直接冲突。

**一对多时取第一行。** 被否决：判定会作用在任意选中的记录上，而结果看起来正常。

**冲突时让主源静默胜出。** 被否决：判定会悄悄基于一个没人确认过的值。
把 `ConflictingValue` 做成可比较的类型也被否决——那等于替使用者做了选择。

**允许多个主源。** 被否决：同一实例会有两个 token，留痕无法对齐。

**在数据库里下推 join。** 被否决：跨源本来就无法下推，两侧可能是不同数据库产品，
甚至一侧是 CSV 或 REST。

**副源不可达时回落到本源同名表。** 被否决：读错的表会产出看似合理的数字。

## Consequences

正面：

- 一个对象可以跨两个数据源，聚合也可以跨源
- 「同一实例」的依据进入判定记录，跨源判定可被追问
- 一对多与冲突都是显式错误，不是静默的错误结论
- `SchemaBundle` 具备加列能力，此后新增字段在升级部署上也生效

负面：

- 匹配在内存中进行（逐行读副源后比对），有 `MAX_MATCH_CANDIDATES` 上限；
  副源匹配列上没有索引时会很慢
- 每次判定都会为每条跨源对应打开一次副源连接——无连接池（技术债 8）时代价明显
- 匹配键必须由建模人员声明。源数据里没有可靠共同键时，本机制无法帮忙——
  这是刻意的：没有可靠共同键时，任何自动匹配都是猜测
- 三个以上数据源需要声明多条对应，平台不做传递推导
  （A↔B、B↔C 不会自动得出 A↔C，因为那会引入一条没人声明过的对应关系）
