# ADR-0005 语义通用性封顶：不做完整 OWL/DL 推理

- 状态：Accepted
- 日期：2026-08-21

## Context

项目做的是「领域本体」，自然会被问：为什么不用 OWL？为什么不接一个
DL reasoner（HermiT、Pellet、ELK）？那样通用性不是更强吗？

本项目的核心承诺是**答案可核验**：判定类结论必须能回答「你凭什么这么说」，
并且答案要能落到具体依据上——某条规则、某个字段值、某份文档的某一条。

## Decision

不做完整的 OWL/DL 推理，不采用开放世界假设。

通用性靠两件事实现：

**结构表达力** —— 让本体能表达更多东西：实例解析器（一个对象来自多表、
复合主键、判别列分区、跨源）、值域映射、关系基数与多对多、类型层级、
派生属性、时态。这些都是可以逐项验证、逐项解释的结构。

**逃生舱** —— 当结构表达力不够时，允许用户下沉到自定义实现：

| 逃生舱 | 作用 |
|---|---|
| 自定义 SQL 或视图作对象来源 | 任意复杂的实例定义 |
| 自定义规则函数 | 内置 5 个函数之外的判定逻辑 |
| 派生属性表达式 | 计算字段 |
| 写回执行器 SPI | HTTP 之外的写回通道（MQ／RPC／存储过程） |
| 数据源适配器 SPI | 三种数据库之外的来源 |
| 检索后端与嵌入模型 SPI | 自带检索栈 |

## Alternatives considered

**引入 DL reasoner 做子类推断与一致性检查。** 拒绝理由，这是本决定的核心：

DL reasoner 的结论是**全局蕴含**的产物。当它推出「这个客户属于高风险类」时，
这个结论来自本体中所有公理的联合作用，而不是某一条可指认的规则。
要解释它，要么给出一棵完整的推导树（业务人员看不懂，也无法在工单里引用），
要么只能说「按本体推理如此」。

这与本项目要交付的那句话直接对立：

> 「订单 A123 不满足退款条件，因签收已超 15 天（规则 `refund_window_check`），
> 依据《售后政策》第 3.2 条。」

客服要能说出规则编码和文档条款号。DL 推理给不出这种粒度的归因。
**通用性提升的代价是可核验性丧失，而可核验性是本项目唯一的护城河。**

另一层：开放世界假设意味着「没查到就是未知」。业务判定需要的恰恰是
封闭世界语义——数据库里没有这条付款记录，就是没付款，不是「未知是否付款」。
把 OWA 引入业务判定会让「不满足条件」这个结论无法成立。

**做一个受限的推理子集（如仅 RDFS 子类传递）。** 部分保留。
类型层级（通用性 #6）会带来子类型的属性继承，这是确定性的结构展开，
不是搜索式推理，可以解释为「因为 A 是 B 的子类型」。
这条边界的判据是：**结论能否归因到单条可指认的依据。**

**做通用图数据库／任意三元组存储。** 拒绝理由：见 Non-Goals。
一旦允许任意三元组，就无法保证每个结论都有可解释的来源，
且失去与关系型遗留系统的映射关系——而映射关系正是证据链的载体。

## Consequences

正面：每个判定结论都能给出结论 + 依据规则 + 证据链 + 决策记录。
定位清晰：这不是知识图谱平台，是可核验的判定内核。

负面：无法回答需要跨多跳蕴含的问题。无法做本体一致性的形式化验证。
不能导入外部 OWL 本体并直接使用其推理能力（目前只能导出 JSON-LD／Turtle，
无导入、无 SHACL、无 reasoner）。

负面：对熟悉语义网技术栈的用户，需要解释为什么不用他们期待的工具。
这份 ADR 就是那个解释。
